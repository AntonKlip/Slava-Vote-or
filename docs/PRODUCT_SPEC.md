# Продуктовая спецификация — Slava Vote

Статус: живой документ, обновляется по мере уточнения правил. Последнее обновление: 2026-08-20.

## Назначение

Telegram-бот для проведения **одного** конкурса фотографий (одноразовое мероприятие, не переиспользуемая площадка). Ожидаемое число участников — порядка 30–50 человек.

Администраторы добавляют фотографии участников с их именами. Пользователи просматривают участников. В нужный момент администратор открывает голосование. После завершения голосования бот показывает TOP 2 по каждой номинации — без количества голосов для обычных пользователей.

## Роли

| Роль | Может |
| --- | --- |
| **USER** | запускать бота; просматривать фото; голосовать, если голосование доступно; смотреть результаты после FINISHED |
| **ADMIN** | всё, что USER, + добавлять/редактировать/удалять (soft delete) фото; запускать и останавливать голосование; выдавать индивидуальное разрешение на ранний доступ к голосованию; смотреть результаты в любой момент; управлять административными настройками |

Проверка роли — всегда на сервере (в `services`/`middleware`), никогда не по клиентскому вводу и не по скрытию кнопки в интерфейсе.

Первый администратор задаётся через `ADMIN_TELEGRAM_IDS` (env) при `/start`. Идентификатор пользователя — `telegram_id`, никогда username (username может меняться).

## Основной сценарий (актуальная модель, без Contest)

Это не набор параллельных конкурсов — это **один общий пул фотографий** и **одно голосование** с несколькими номинациями:

```
ОБЩАЯ БАЗА ФОТО (глобальная, не привязана ни к чему)
  Фото 1, Фото 2, Фото 3, ...

        ↓ администратор открывает состояние VIEWING

Пользователь просматривает участников

        ↓ администратор запускает голосование (VOTING)

Пользователь открывает фото → выбирает номинацию → голос засчитан
  📷 Иван
  [🏆 Номинация 1] [😂 Номинация 2] [🎨 Номинация 3] ...

        ↓ администратор останавливает голосование (FINISHED)

Результаты: по каждой номинации — TOP 2 (без чисел голосов)
```

Состояние всего голосования (не конкретной фотографии и не конкретной номинации) — одно на всё приложение: `DRAFT → VIEWING → VOTING → FINISHED`. Подробности сущностей — в [ARCHITECTURE.md](./ARCHITECTURE.md).

## Добавление фотографии (ADMIN)

```
Добавить участника → Telegram photo → Имя участника → Preview → Подтверждение → Сохранение
```

Хранится `telegram_file_id` (для повторной отправки) и `telegram_file_unique_id` (для идентификации), без бинарного хранения изображений в БД. Удаление — только soft delete (`Photo.status = DELETED`), чтобы не ломать историю голосования: удалённое фото никогда не показывается в списках/Mini App и не участвует в подсчёте результатов, но связанные с ним `Vote` физически не удаляются.

Планируемая реализация этого экрана — Phase 6 (см. TASKS.md): один шаг вместо цепочки выше — ADMIN отправляет боту фото с подписью (caption) = имя участника; без подписи фото не сохраняется. Многошаговый диалог (Preview/Подтверждение) не реализуется, чтобы не тянуть отдельную зависимость для conversation-flow в grammY.

## Номинации

Отдельные сущности (не зашиты в код), глобальные — не привязаны к конкретному "конкурсу", так как конкурс один. Точное количество и названия номинаций **пока не определены** — см. раздел TBD.

## Индивидуальный доступ к голосованию

Администратор может открыть голосование конкретному пользователю раньше общего старта. Матрица **права голоса**:

| Состояние голосования | USER без permission | USER с permission | ADMIN |
| --- | ---: | ---: | ---: |
| DRAFT | ❌ | ❌ | ❌ |
| VIEWING | ❌ | ✅ | ✅ |
| VOTING | ✅ | ✅ | ✅ |
| FINISHED | ❌ | ❌ | ❌ |

ADMIN голосует наравне с USER+permission — нет причин это запрещать, зафиксировано явно (см. DECISIONS.md D27), а не как случайный побочный эффект проверки роли.

Единая точка проверки — функция `canVote(user, votingState, hasPermission)` (`voting.service.ts`), не дублируется по хендлерам/роутам. Реализовано в Phase 5.

### Просмотр фотографий — отдельная от права голоса проверка

Доступ к самому списку/карточкам фото — не то же самое, что право голосовать (см. DECISIONS.md D27). Матрица (актуальна с Phase 7, Mini App):

| Состояние голосования | USER | ADMIN |
| --- | ---: | ---: |
| DRAFT | ❌ нет доступа | ✅ |
| VIEWING | ✅ просмотр | ✅ |
| VOTING | ✅ просмотр + голосование | ✅ |
| FINISHED | ❌ (доступны только результаты) | ✅ |

ADMIN имеет доступ к просмотру фото независимо от состояния голосования.

## Результаты

После перехода в FINISHED: TOP 2 по каждой номинации, без количества голосов. Детерминированный tie-breaker при равенстве — `photo.id ASC` (простое техническое решение до появления официальных правил). Сами голоса не удаляются из БД.

## Явные ограничения MVP

- один Telegram-аккаунт = один пользователь; защиты от нескольких аккаунтов на одного человека нет; античит вне скоупа MVP;
- `telegram_file_id` — временное решение для хранения фото, без отдельного файлового storage (в будущем возможен переход на S3/R2-совместимое хранилище);
- отдельный веб-интерфейс (Telegram Mini App) запланирован — см. Phase 7 в TASKS.md и DECISIONS.md D19–D25; до его реализации основной интерфейс — чат-команды бота;
- финальный UI просмотра/голосования не определён (нужно оставить возможность протестировать несколько вариантов: грид, список, карточки — запланировано в Phase 7);
- количество голосов не показывается обычным пользователям.

## TBD — сознательно не определено

Эти пункты **не придумываются заранее** — фиксируются как открытые вопросы, архитектура должна оставаться расширяемой под любой из вариантов:

- сколько фотографий пользователь может выбрать в одной номинации (одну, несколько, без ограничений);
- можно ли пользователю изменить/отозвать свой голос, и как именно;
- итоговые названия и количество номинаций;
- финальный UI каталога/просмотра/голосования;
- точный критерий tie-break, если `photo.id ASC` окажется неприемлемым после определения официальных правил конкурса.

Технически на уровне БД зафиксирована только одна гарантия: пользователь не может дважды создать одинаковую запись голоса за одно и то же фото в одной и той же номинации (`UNIQUE(userId, photoId, nominationId)`). Ограничение `UNIQUE(userId, nominationId)` сознательно не используется — оно бы зафиксировало недоопределённое правило "одна фотография на номинацию".
