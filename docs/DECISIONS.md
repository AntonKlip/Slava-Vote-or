# Журнал решений — Slava Vote

Формат: ADR-style, коротко. Каждое решение — что решили и почему. Все решения ниже приняты 2026-08-20 в ходе первой сессии разработки.

## D1. Пакетный менеджер — npm

Пользователь не различает npm/pnpm/yarn и попросил не усложнять. npm идёт вместе с Node, не требует отдельной установки. Статус: принято.

## D2. Модульная система — ESM

TypeScript/Node настроены на `"type": "module"` + `module`/`moduleResolution: NodeNext`. grammY нативно ориентирован на ESM, современный стандарт. Статус: принято.

## D3. Test runner — Vitest

Выбор пользователя. Нативно понимает TS/ESM, минимальный конфиг. Статус: принято.

## D4. База данных — только Neon, без Docker/локального Postgres

На машине разработки нет Docker. Пользователь подтвердил, что онлайн-БД понадобится в любом случае скоро — решили не ставить локальный Postgres вообще и сразу работать с Neon (бесплатный тариф) и для разработки, и в будущем для продакшена. Статус: принято.

## D5. Git/GitHub — работа в корне репозитория

Репозиторий уже был создан пользователем на GitHub (`AntonKlip/Slava-Vote-or`) и содержал только автосгенерированный `.gitattributes`. При подключении обнаружился дублирующий локальный клон в подпапке `Slava Vote or` (создан IDE/пользователем независимо от Claude, заблокирован открытым процессом) — решили работать в корне `d:\Web_Developer\Slava`, пользователь удалил дубликат самостоятельно (подтверждено проверкой `git status`/`ls`). Статус: принято.

## D6. Хранение секретов — DATABASE_URL никогда не передаётся Claude

Пользователь явно выбрал: он сам создаёт Neon-проект, вписывает `DATABASE_URL` в свой локальный `.env` и сам запускает `npm run prisma:migrate`. Claude пишет и валидирует схему (`prisma validate`/`format`/`generate` — не требуют подключения к БД), но не видит реальный connection string и не выполняет миграции против настоящей базы. Статус: принято, действует для всех последующих фаз.

## D7. npm audit — 3 high severity в транзитивной dev-зависимости Prisma CLI не фиксируются принудительно

`deepmerge-ts` (используется `@prisma/config` → `prisma` CLI) имеет stack exhaustion при рекурсивном merge. Это dev-тулинг, не рантайм бота, не подвергается вводу от участников конкурса. `npm audit fix --force` откатил бы Prisma на более старую версию ради низкой практической угрозы — решили не делать. Статус: принято, пересмотреть при апдейте Prisma в будущем.

## D8. Модель данных — без Contest, без PhotoNomination, один VotingState

Прошла через три итерации в рамках одной сессии планирования:

1. **Черновик 1**: `Photo.contestId` — фото жёстко привязано к конкретному Contest. Отклонено пользователем: приложение изначально задумано с несколькими параллельными "конкурсами", но по факту фото должны быть общим пулом, переиспользуемым между конкурсами.
2. **Черновик 2**: `Photo` — глобальная сущность, `Contest` остаётся, связь с номинациями через join-таблицу `PhotoNomination` (many-to-many Photo↔Nomination). Отклонено пользователем: в реальности нет отдельного этапа "подать фото на номинацию" до голосования — пользователь сразу при голосовании выбирает фото и номинацию. Модель предполагала лишний этап, которого нет в продукте.
3. **Финальная модель**: приложение — это **одно** голосование (не несколько параллельных конкурсов) с несколькими номинациями. `Contest` убран полностью. `PhotoNomination` убран полностью. Состояние голосования (`DRAFT/VIEWING/VOTING/FINISHED`), ранее жившее на `Contest`, переехало в отдельную сущность `VotingState` — одна строка на всё приложение.

Итоговые сущности: `User`, `Photo` (глобальный пул), `Nomination` (глобальный список), `Vote` (`userId`+`photoId`+`nominationId`), `VotingPermission` (per-user, без привязки к конкурсу), `VotingState` (одна строка статуса). Статус: принято, это модель для Phase 2.

## D9. Имя сущности статуса голосования — VotingState

Альтернатива — `VotingSession` (подразумевает возможность нескольких последовательных голосований в будущем). Пользователь подтвердил `VotingState`: одна строка-состояние, singleton не обязателен на уровне БД. Статус: принято.

## D10. `telegramFileUniqueId` — индекс, не unique constraint

Формально это идентификатор Telegram для дедупликации, но жёсткий unique на уровне БД мог бы неверно заблокировать легитimные кейсы. Политика дедупликации (если понадобится) — на уровне `photo.service`, не схемы. Статус: принято, может быть пересмотрено при реализации `photo.service`.

## D11. `VotingPermission` — один на пользователя (`userId` unique), без привязки к конкурсу

Следствие D8: раз голосование одно, разрешение на ранний доступ тоже одно на пользователя, а не одно на пару (пользователь, конкурс). Статус: принято.

## D12. Без `onDelete: Cascade` — нигде

Soft delete (`Photo.status = DELETED`) — единственный санкционированный способ "удаления" фото. Каскадное удаление могло бы незаметно стереть историю голосов (`Vote`). Статус: принято.

## D13. Уникальность голоса — только `UNIQUE(userId, photoId, nominationId)`

Правила голосования (сколько фото можно выбрать в одной номинации, можно ли менять голос) намеренно не определены — см. PRODUCT_SPEC.md, раздел TBD. `UNIQUE(userId, nominationId)` не используется, так как это преждевременно зафиксировало бы правило "одна фотография на номинацию". Статус: принято, единственная техническая гарантия на данный момент.

## D14. Prisma 7 конвенции — output в `src/generated/prisma`, конфиг подключения в `prisma.config.ts`

`npx prisma init` (Prisma 7.9.1) сам сгенерировал `generator client { provider = "prisma-client", output = "../src/generated/prisma" }` и пустой `datasource db { provider = "postgresql" }` без `url` — вместо этого URL читается из `prisma.config.ts` (`datasource.url: process.env["DATABASE_URL"]`). Решили не переписывать под старый (Prisma 5/6) стиль — это актуальная конвенция установленной версии. `/src/generated/prisma` добавлен в `.gitignore` автоматически; добавлен `postinstall: prisma generate` в `package.json`, чтобы клиент пересоздавался у любого, кто клонирует репозиторий и делает `npm install`. `src/generated/` также исключён из ESLint (генерируемый код, не наш стиль). Статус: принято.

`prisma init` также без предупреждения подтянул с GitHub (`prisma/skills`) файлы-подсказки для AI-агентов — не тонкие ссылки, а три полные копии (~477 КБ каждая) под `.agents/`, `.claude/`, `.windsurf/`, плюс `skills-lock.json`. Секретов не содержат, официальный контент от Prisma, но это чистый балласт для репозитория (3x дублирование, не нужно для работы приложения) — исключены из git через `.gitignore`, оставлены на диске локально. Статус: принято.

## D15. Отступление от D6 — пользователь вставил реальный `DATABASE_URL` в чат

На практике пользователь прислал настоящую строку подключения к Neon прямо в переписке (не только в свой `.env`), нарушив изначальную договорённость D6. Поскольку секрет уже оказался в истории чата, скрывать его задним числом бессмысленно — по запросу пользователя Claude использовал его напрямую: вписал в локальный `.env`, выполнил `prisma migrate dev --name init` против реальной Neon-базы (миграция `20260820192542_init` применена и закоммичена). Пользователь принял решение сменить пароль роли `neondb_owner` в Neon Console самостоятельно после сессии (на момент записи ещё не сделано). Статус: принято как разовое отступление; правило D6 (секреты не передаются в чат) остаётся действующим по умолчанию для всех последующих фаз.

## D16. Driver adapter для Prisma Client — `@prisma/adapter-pg` (не `@prisma/adapter-neon`)

Prisma 7 требует явный driver adapter для SQL-провайдеров — `new PrismaClient()` без adapter больше не работает. Для Neon есть два варианта: `@prisma/adapter-neon` (HTTP/WebSocket, рассчитан на edge/serverless окружения) и `@prisma/adapter-pg` (обычный TCP через пакет `pg`). Выбран `@prisma/adapter-pg`: бот работает как обычный долгоживущий Node-процесс на long polling (см. D4, ARCHITECTURE.md), а не как edge/serverless функция — стандартный TCP-адаптер проще и не даёт лишних ограничений serverless-протокола. Реализовано в `src/database/prisma.ts`. Статус: принято.

## D17. Инцидент — `env.txt` с новым паролем Neon вне `.gitignore`

После смены пароля роли `neondb_owner` в Neon Console (упомянуто в D15 как ожидаемое действие) пользователь сохранил новые `PGUSER`/`PGPASSWORD` в файл `env.txt` в корне репозитория. Файл не подпадал под `.gitignore` (там исключён точно `.env`, а не `env.txt`) — при случайном `git add .`/`git add -A` пароль ушёл бы в GitHub. Claude обнаружил файл через `git status` (untracked), прочитал его для диагностики, не привёл содержимое в чате, и попросил пользователя вручную перенести пароль в `.env` (сохраняя правило D6 — секреты не передаются в чат) и удалить `env.txt`. Пользователь выполнил, файл удалён, подключение к Neon с новым паролем подтверждено. Статус: закрыто. Вывод на будущее: при работе с секретами вне `.env` — всегда проверять `git status`/`.gitignore` до дальнейших действий.

## D18. Роль `MODERATOR` удалена — только `USER`/`ADMIN`

Перед Phase 4 пользователь решил упростить ролевую модель: убрать `MODERATOR` из `UserRole` (`prisma/schema.prisma`), оставив только `USER` и `ADMIN`. Все действия, ранее доступные MODERATOR/ADMIN (управление фото, запуск/остановка голосования, выдача индивидуального доступа), теперь доступны только ADMIN. На момент изменения пользователей в базе ещё не было (Phase 3 только добавила bootstrap ADMIN через `ADMIN_TELEGRAM_IDS`, ни один аккаунт ещё не создавался), поэтому потери данных при миграции enum не было. Применено: `prisma/schema.prisma` (`enum UserRole { USER ADMIN }`), миграция `20260820200145_remove_moderator_role` (пересоздание enum-типа — Postgres не поддерживает `DROP VALUE`), `src/middleware/permissions.ts` (`ROLE_RANK` без записи `MODERATOR`), обновлены `PRODUCT_SPEC.md`/`ARCHITECTURE.md`/`TASKS.md`. Историческая миграция `20260820192542_init` не редактируется задним числом (там `MODERATOR` фигурирует как факт схемы на тот момент). Статус: принято.

## D19. Продуктовое решение — основной UI переезжает на Telegram Mini App

Вместо чат-команд бота основным интерфейсом голосования становится Telegram Mini App (веб-приложение внутри Telegram); бот остаётся точкой входа (`/start` → кнопка запуска) и интерфейсом администратора. При подготовке плана миграции обнаружено два пробела, которых не было ни в одной прошлой фазе: (1) `canVote`/атомарность (Phase 5) ещё не реализованы, (2) способа добавить фото участника или создать номинацию не существует вообще. План разработки продолжен тремя фазами вместо изначальных Phase 5/6: **Phase 5** — `canVote` + атомарность (без изменения содержания, только контекст использования — теперь и ботом, и будущим Mini App API), **Phase 6** (новая) — управление фото/номинациями, **Phase 7** (новая) — сам Mini App. Ничего из существующей архитектуры не выбрасывается (Prisma/PostgreSQL/grammY остаются), HTTP API — новый слой поверх тех же `services/`. Статус: принято, работаем строго по одной фазе за раз (Phase 6/7 не начинаются, пока не завершена и не задокументирована предыдущая).

## D20. HTTP-фреймворк для будущего Phase 7 — Express

Монтируется в том же долгоживущем Node-процессе, что и grammY-бот (`bot.start()` и `app.listen()` в одном `src/index.ts`). Самый задокументированный и мейнстримный вариант, соответствует принципу "не усложнять" (см. [[user-profile]]). Статус: принято, актуально с началом Phase 7.

## D21. Аутентификация Mini App — короткоживущий JWT, не серверные сессии в БД

После валидации Telegram `initData` (HMAC по `BOT_TOKEN`) выдаётся JWT (новый env `APP_JWT_SECRET`); фронтенд хранит его только в памяти и переполучает при каждом открытии Mini App — Telegram и так даёт свежий `initData` при каждом запуске. Не требует таблицы сессий. Frontend никогда не может передать `userId`/`telegramId`/`role` напрямую — они определяются только сервером из валидированного `initData`. Статус: принято, актуально с началом Phase 7.

## D22. Фронтенд Mini App — React + TypeScript + Vite, отдельный npm workspace

`frontend/` как отдельный npm-workspace (`root package.json` → `"workspaces": ["frontend"]`). Собранные статические файлы отдаёт тот же Express-процесс — один origin, не нужен CORS. Самый мейнстримный вариант, проще всего гуглить/чинить проблему в будущем; UI-компоненты (грид/список/карточки фото) намеренно оставлены переключаемыми — финальный визуал не решён, см. PRODUCT_SPEC TBD. Статус: принято, актуально с началом Phase 7.

## D23. Показ фото в Mini App — серверный прокси с in-memory кэшем `file_path`

`GET /api/photos/:id/image` резолвит `telegram_file_id → file_path` через `bot.api.getFile` и стримит байты; токен бота никогда не попадает в браузер. Результат `getFile` кэшируется в памяти процесса по `telegramFileId` с TTL — при листании десятков/сотен фото не долбим Telegram API на каждый повторный просмотр. Простой `Map` в процессе, без Redis/доп. таблицы. S3/R2 не вводится (см. ARCHITECTURE.md, "Хранение фотографий"). Статус: принято, актуально с началом Phase 7.

## D24. Admin UI фото/номинаций остаётся в боте; Mini App admin — только архитектура

Добавление/редактирование фото и номинаций реализуется как ADMIN-only bot-команды (Phase 6), а не как часть Mini App. Mini App admin UI (T7.13) на этом этапе только архитектурно предусматривается (маршруты/права задокументированы), но не реализуется — избегаем реализации "всего сразу" там, где продукт explicitly просит не переусложнять раньше времени. Статус: принято.

## D25. `POST /api/votes` не придумывает лимит "фото на номинацию"; архитектура допускает replace/cancel позже

Правило "сколько разных фото можно выбрать в одной номинации" остаётся TBD (см. PRODUCT_SPEC.md) — API его не вводит самостоятельно. Повторный идентичный голос (тот же `user`+`photo`+`nomination`) идемпотентен, не ошибка. Возможность отозвать/изменить голос **не выбрасывается** — она сознательно отложена (нечего менять/отзывать, пока не решено правило про количество), но `voting.service`/API проектируются так, чтобы replace/cancel можно было добавить позже без переделки контракта. Статус: принято.

## D26. Тесты — внутри каждой фазы, а не отдельной фазой

Изначально в TASKS.md была отдельная Phase 6 "Tests" перед сложным UI (соответствует принципу из ARCHITECTURE.md — покрывать критическую бизнес-логику тестами до UI). Решено распределить тесты по каждой фазе как часть её приёмочных критериев вместо отдельного тестового блока-барьера — то же самое покрытие, без лишнего процесса. Первой это правило применено к Phase 5 (T5.4). Статус: принято.

## D27. `canVote` — явная ветка для ADMIN; просмотр фото и право голоса — разные проверки

При реализации Phase 5/подготовке Phase 7 явно зафиксировано две отдельные матрицы (обе должны попасть в PRODUCT_SPEC.md): (1) **право голоса** (`canVote`, per-user) — DRAFT недоступно никому; VIEWING доступно с `VotingPermission` **или ADMIN**; VOTING доступно всем, включая ADMIN; FINISHED недоступно никому. ADMIN голосует наравне с USER+permission — реализовано как явная ветка внутри `canVote`, а не побочный эффект `ROLE_RANK`/RBAC. (2) **просмотр фото** (будущий Phase 7, `GET /api/photos*`) — самостоятельная проверка, не то же самое, что `canVote`: USER — DRAFT нет доступа, VIEWING/VOTING просмотр разрешён, FINISHED доступны только результаты; ADMIN — доступ всегда, независимо от состояния. Статус: принято.

## D28. Атомарная запись голоса — `SELECT ... FOR UPDATE` на строке `VotingState`, не отдельная проверка в роуте

`castVote()` (`voting.service.ts`) оборачивает проверку `canVote` + запись `Vote` в одну Prisma-транзакцию, которая сначала блокирует singleton-строку `VotingState` (`FOR UPDATE`). Конкурентный переход состояния (`voting-state.service`'s `UPDATE ... WHERE status = current`) физически ждёт снятия этой блокировки — гонка "голос vs остановка голосования" не может дать голосу проскочить после фактического перехода в FINISHED. Дублирующий голос (`(userId, photoId, nominationId)` уже существует) обрабатывается через явную проверку `findUnique` внутри той же транзакции и возвращает идемпотентный успех — **не** через попытку `create()` и отлов unique-constraint как основной путь. `castVote` заодно проверяет `Photo.status = ACTIVE` и `Nomination.active` — вся бизнес-логика голоса в одном месте, готова к переиспользованию будущим `POST /api/votes` (Phase 7) без дублирования. Статус: принято.

## D29. Таймстемпы `votingStartedAt`/`votingFinishedAt` — через `NOW()` внутри атомарного `UPDATE`, не `new Date()` в JS

Побочная находка при написании гоночного теста для D28: `transitionTo()` в `voting-state.service.ts` исходно вычисляла `new Date()` в Node.js **до** отправки `UPDATE` в Postgres. Под конкуренцией (когда `UPDATE` вынужден ждать снятия блокировки строки, удерживаемой конкурентным `castVote`) эта JS-метка времени фиксировалась раньше фактического момента коммита — до нескольких десятков миллисекунд расхождения в тестах. На саму гарантию атомарности (D28) это не влияло — только на точность отображаемого времени. Исправлено: `transitionTo()` переписан на `prisma.$executeRaw` с `NOW()` внутри того же `UPDATE ... WHERE id = ... AND status = ...` (используются `Prisma.sql`/`Prisma.raw`/`Prisma.empty` из сгенерированного клиента для условного добавления `votingStartedAt`/`votingFinishedAt` к `SET`). Статус: принято.

## D30. Тесты Phase 5+ — напрямую против реального Neon, без mock/тестовой БД

Продолжение D4 (нет локального Postgres): unit/integration-тесты для сервисов, трогающих БД, используют тот же `prisma`-синглтон и реальный Neon вместо мока Prisma Client. Тестовые пользователи создаются с **отрицательным** `telegramId` (реальные Telegram id всегда положительные — гарантированно нет коллизий с настоящими аккаунтами) и удаляются в `afterAll`/`try…finally`. Поскольку несколько тестовых файлов (`voting.service.test.ts`, `voting-state.service.test.ts`) читают и пишут одну и ту же singleton-строку `VotingState`, добавлен `vitest.config.ts` с `fileParallelism: false` — иначе параллельные воркеры vitest гонялись бы друг с другом независимо от тестируемой логики. Тестовые файлы (`*.test.ts`) исключены из продакшен-сборки через новый `tsconfig.build.json` (расширяет `tsconfig.json`, добавляет `exclude`) — `npm run build` использует его, чтобы `dist/` не содержал `*.test.js` (иначе vitest подхватывал и `.ts`, и скомпилированные `.js`-копии тестов, задваивая прогон и обращения к реальной БД — было обнаружено и исправлено в Phase 5). `npm run typecheck` по-прежнему использует основной `tsconfig.json` и продолжает проверять тесты. Статус: принято.
